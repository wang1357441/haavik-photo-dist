# HAAVIK Photo

一个**真能用的图片工具**，外加一道每月出现一次的小闸门。

双击 `Setup.exe` → 走完安装向导 → 桌面上多出**一个** `MyAlbum.exe`（就这一个文件，没有快捷方式）。
首次启动会问一句「天空属于什么」：答对直接进工具；答错则软件进入「已锁定」，要一串序列号。

> 这是一个**玩笑**，不是恶意软件。但它确实带着「真关机」这个能力（**默认关闭**），
> 所以请先读完下面的「使用前提」。

---

## ⚠️ 使用前提（先读这段）

1. **只对事先知情并同意的朋友用。** 未经同意对别人使用，性质就是骚扰，不是玩笑。
2. **请勿用于生产环境、他人设备，或任何你无法当面解释清楚的场合。**
3. **默认绝对不会关机。** 答错只会看到「软件已锁定」页。
   只有显式带 `--real-shutdown` 启动，答错才会走老的 60 秒关机倒计时；
   那条路径下倒计时交给 Windows 自己走（`shutdown /s /t N`），
   所以中招的人随时可以执行 `shutdown /a` 中止，倒计时界面本身也有取消按钮。
4. 序列号是一道**题**，不是一把锁 —— 生成器就公开在仓库里（见下方「序列号机制」）。
   它的作用是让朋友"费一下手"，不是阻止任何人使用。

## 它做什么

**安装器 `Setup.exe`**

1. 检测 Windows 版本，Vista 以下直接弹「系统不兼容」并退出
2. 检测目标系统是 32 位还是 64 位
3. 4 步向导：欢迎 → 安装位置 → 组件 → 进度 → 完成
4. 释放对应架构的主程序，**就只放这一个文件**，默认位置是**桌面**
   （可改，但默认就是桌面 —— 双击即用、右键即删）
5. **不创建任何快捷方式**：程序自己就在桌面上，再放一个指向它的 `.lnk` 是纯重复，
   而且会留下"删了 exe 还留着坏快捷方式"的状态

**主程序 `MyAlbum.exe`** —— 图片工具部分

1. 打开图片（JPEG / PNG / WebP / BMP），读 EXIF 方向自动摆正
2. **改尺寸**：按像素（宽×高）或按百分比；锁纵横比时可只填一边
3. **格式转换**：JPEG / PNG / WebP / BMP 互转，JPEG 与 WebP 可调质量
4. 旋转 90°、还原原图、快捷缩放按钮（25% ~ 200%）
5. **另存为** —— 默认文件名是 `原名_改.ext`，**永不默认覆盖原图**；
   即便执意选回原路径，还要再确认一次，而那个确认框的默认按钮是「否」

**主程序** —— 闸门部分（每月一次）

1. 本月还没过闸 → 出一张图 + 一句「天空属于谁？」，三个选项：`A. 哈夫克` / `B. 阿萨拉` / `C. GTI`
2. 答对 → 本月过闸，直接进图片工具，**不需要任何序列号**
3. 答错 → 「🔒 软件已锁定」：一排 5 组共 25 位的序列号输入框 + 生成器在哪的提示
4. 过闸记录写在安装目录的 `state.json` 里，所以**一个月只问一次**，不是每次启动都问

命令行参数：`--real-shutdown`（启用真实关机，默认关）、`--seconds N`（倒计时秒数，默认 60）、
`--no-image`、`--no-update-check`（完全离线运行）、`--reset-gate`（清掉本月的过闸记录，等于重新出题）、`--debug`。

## 序列号机制（生成器 ↔ 校验器）

需求是"生成器放公开仓库、朋友自己生成" —— 而生成器与校验器必须在算法上完全对齐，
否则会出现「生成器吐的号，程序不认」这种最难查的故障。

做法是**把两者放进同一个文件**：`code_review/optimized/serial_check.py`。

- 它既是可以直接双击运行的生成器（`python serial_check.py`），
  也是主程序 `import` 的校验器（`verify()`）。同一份代码，前后向不可能漂。
- 它是**自成一体的**：只 import 标准库，不 import 任何兄弟模块。
  审计脚本对这条下了断言（见下方 C 节「自成一体的模块断言」），
  因为它要被**单独一个文件**复制到公开仓库去 —— 本地永远测不出"少带了一个兄弟模块"。
- 它带 `--selftest`，跑 200 轮"生成→校验"，外加篡改、错月份、乱输入等边界：

```powershell
python code_review/optimized/serial_check.py --selftest
```

> 「生成的序列号一定校验得过」在这里是**能当场自证的事实**，不是一个承诺。

**格式**：Crockford Base32（去掉了易混的 `I/L/O/U`），15 字节载荷 → 24 位 + 1 位手抄校验位，
共 **25 位、分 5 组**。序列号本身 = `MAGIC ‖ 6 字节随机 ‖ 8 字节 HMAC-SHA256 标签`，
标签绑定了**月份**，容忍 ±1 个月（防跨月边界误伤）。

**它不提供任何安全性 —— 这一点必须说清楚。**
`SERIAL_SECRET` 就明文写在公开的源文件里，任何人读一遍就能自己造号。
这是有意的：它是一道**题**，不是一把锁；想拦住人在这个场景下既无必要也不诚实。

锁定页给出的地址是 `main.REPO_HINT_URL`，当前指向 `https://github.com/hhhs81`
（GitHub 主页一定存在，不会给朋友一个 404）。等"公开分发仓库"建好，
把它改成那个仓库地址，朋友就能一路点到生成器。

## 它明确**不**做什么

这一节是重点 —— "我要不要相信这个 exe"不该靠印象，应该靠证据。

| 不做的事 | 依据 |
|---|---|
| 不做持久化 | 不写 Run 键、不建计划任务、不碰启动目录。跨次启动只写**一个** `state.json`（见下） |
| 不创建快捷方式 | 安装只是往你选的文件夹（默认桌面）放**一个 exe**；不写 `.lnk`、不建目录树 |
| 不写注册表 | 源码侧不导入 `winreg` |
| 不装输入钩子 | 不导入 `keyboard` / `pynput` / `pyautogui` |
| 不破坏数据 | **不默认覆盖原图**：默认另存为 `原名_改.ext`，覆盖源文件要二次确认且默认「否」 |
| 不窃取机器标识 | 版本查询不带任何参数、Cookie、机器码或用户信息，就是一个裸的 GET |
| 不静默安装更新 | 更新包下载后要由**用户亲手点**才运行，程序绝不静默替换自己 |

**它确实会写盘，只有三个地方**（这是审计里的硬断言，不是自我描述）：

1. `state.json` —— 记"这个月问过了"，**和 exe 放在同一个文件夹里**（默认就是桌面，
   所以它看起来就是桌面上的第二个文件）；删掉它等于重新出题；
2. 你在「另存为」里**亲自选**的那张图；
3. 你**亲自点过**「下载」的更新包（下载前先校验 sha256 与大小，校验不过就删掉本次下载）。

安装器则只写主程序本体（默认落在桌面）与它自己的诊断日志
`%LOCALAPPDATA%\HAAVIK Photo\install.log`（仅用于安装失败时说明原因）。

> `state.json` 摆在你眼皮底下是有意的：本项目不做"藏起来的痕迹"，
> 你能看见它、能删掉它，也就等于能验证"它只记了这么一件事"。

> 归档里确实能搜到 `socket` / `ssl` / `urllib` / `http` 这些名字 —— 但它们**全部**由
> PIL / tkinter 依赖图带进来，源码侧只有 `version_check.py` 一个文件 import 了 `urllib`。
> 审计脚本对这条下了硬断言（见下方 C 节）。

复现方式（本机 64 位工具链）：

```powershell
~/.workbuddy/cache/hvphoto/venv2/Scripts/python.exe code_review/verify_payload.py
```

输出见 [`code_review/VERIFY_REPORT.md`](code_review/VERIFY_REPORT.md)。审计分五节：

> `VERIFY_REPORT.md` 是**生成物**，每次跑脚本都会覆盖。
> 它默认**不写本机绝对路径**（那会把 Windows 用户名和磁盘布局一起带进仓库）——
> 抬头只显示目录名。本地排查要看全路径时加 `--show-paths`。

- **A 容器一致性** —— `payload.zip` 里两个架构的载荷与 `dist/` 逐字节一致，
  容器内的产品标识与 `APP_VERSION` 一致，
  且 zip 实际条目与 `meta.json` 索引完全对应（防"夹带"）
- **B 归档真实索引** —— 读 PyInstaller 的**真实 TOC**（不是全文件字节扫描），四条断言：
  1. 应用侧顶层脚本每个 exe **有且仅有 1 个**（`main` 或 `installer`）；
  2. 引导模块恰好是 `pyimod01`~`pyimod04` + `struct` 这固定的 5 个；
  3. `--add-data` 的必需资源（主程序 `haavik.png`、安装器 `payload.zip`）确实在归档里；
  4. **本项目自己的模块**：源码可达集合 == 归档内含集合（少了 = 打包漏带，多了 = 夹带）
- **C1 源码导入审计** —— 用 `ast` 解析源码的直接导入集合，与归档里的模块表做**三态比对**
  （源码 / 依赖 / 无），并用 `SINGLE_FILE_ONLY` 断言 `urllib` **只允许出现在 `version_check.py`**
  （联网能力不得散落）
- **C2 自成一体的模块断言** —— `serial_check.py` 不得 import 任何同目录兄弟模块，
  并打出它的行数与 sha256，供发布到公开仓库后核对是不是同一份
- **C3 写盘 / 起进程审计** —— 用 `ast` 找出所有**确定形态**的写盘与起进程调用，
  与 `WRITERS_EXPECTED` 逐条比对（上面"只会写三个地方"就是这么来的）
- **D 版本信息与签名主体** —— 纯 Python 解 VS_VERSIONINFO，核对署名

当前结论见上一节表格与 `VERIFY_REPORT.md` —— 报告里每一项都带来源文件名与行号。

> 为什么不用"拿模块名去 exe 里数字节出现次数"这种办法：那个做法是**双向错**的。
> 误报（依赖图带进来的模块全算命中）、漏报（`chr()` 拼出来的字符串扫不到）。

## 为什么只需要一个安装包

Windows 的 WoW64 **只向下兼容**：

```
32 位 exe  →  32 位 Windows   能跑（原生）
           →  64 位 Windows   能跑（WoW64）
64 位 exe  →  32 位 Windows   加载失败（连入口都进不去）
```

所以"一个安装包通吃"的唯一解，是把**安装器**编译成 32 位，由它在运行时判断目标架构再释放对应的主程序。

判断必须读 `PROCESSOR_ARCHITEW6432`（**系统**视角），不能只看 `PROCESSOR_ARCHITECTURE`（进程视角）—— 否则 32 位安装包在 64 位系统上会误判。

## 更新是怎么工作的

主程序启动时会在后台做一次版本查询（`version_check.py`，本项目**唯一**的联网点）：

- 固定 URL 做一次 HTTPS GET，只读回一小段文本，超时 8 秒；
- 查到新版本时，在标题栏与页面上显示一行提示；
- 不发送任何机器标识；失败（没网 / 被墙）就静默降级，不影响使用；
- `--no-update-check` 可完全关掉这个查询。

**如果远端提供的是 manifest（而不是一个光秃秃的版本号），程序还能真的下载更新包**：
先比大小、再校验 sha256，`sha256` 对不上就删掉这次下载并报错；
下载完成后**由用户亲手点**才会运行 —— 程序从不静默替换自己。

> 但**目前 `MANIFEST_URL` 是空的**，所以实际行为只有「提示有新版本」这一档。
> 原因很直接：分发仓库是私有的，私有仓库的 Release 附件匿名下载不到；
> 而在 exe 里内置一个带权限的 token，等于把凭证随程序发给每个人 —— 这个不做。
> 要让"自动下载"真正可用，需要先建一个**公开**的分发仓库（只放安装包 + manifest + 序列号生成器）。

版本锚点是一个**只存版本号字符串**的公开 Gist。之所以能公开：里面除了当前最新版本号以外没有任何信息。

> 刻意**不做**的两件事：① 不做开机自启 + 后台联网 —— "自启动 + 联网 + 下载执行"
> 三件凑齐就是恶意软件的标准特征，等于把刚清掉的杀软误报亲手装回去；
> ② 不做**静默**自我替换 —— 更新包落地后必须由用户点击才运行，程序没有"悄悄换掉自己"的路径。
> 想省事也可以直接**重新发一个新的 `Setup.exe`**，零常驻进程。

## 重新打包

```powershell
# 完整构建：图标 → 双架构主程序 → 签名主程序 → 打包载荷 → 构建安装器 → 签名安装器
~/.workbuddy/cache/hvphoto/venv2/Scripts/python.exe code_review/optimized/build.py
```

工具链：

- **32 位**（安装器必须用它编译）：`~/.workbuddy/cache/py38/python.exe`
  — Python 3.8.10 + PyInstaller 5.13.2 + tkinter + Pillow
- **64 位**：`~/.workbuddy/cache/hvphoto/venv2/Scripts/python.exe`
  — Python 3.12.14 + PyInstaller 6.22.2 + tkinter + Pillow

三个**硬约束**（都是踩坑换来的）：

1. **签名顺序不能挪** —— 主程序必须在打包载荷**之前**签好。载荷容器里的 CRC32 是打包那一刻算出来的，
   先签后打包才保得住"容器内字节 == dist 字节"这条不变量。正确顺序：
   主程序 → 签名主程序 → 打包载荷 → 构建安装器 → 签名安装器。
2. **资源必须显式断言已嵌入** —— 主程序要用 `--add-data` 把 `haavik.png` 打进 exe。
   曾经漏过一次：程序默默显示「图片加载失败」，而当时其它所有校验（PE 位数、签名、载荷哈希、安装链路）**全部通过**。
   现在 `build.py` 的 `assert_embedded()` 缺了就构建失败。
3. **产品名只有一处真源** —— `"HAAVIK Photo"` 同时出现在四个模块里
   （`main.APP_TITLE` / `installer.APP_NAME` / `state_store.APP_DIRNAME` / `image_tool.APP_TITLE`），
   它们必须字面相同：各窗口标题、安装日志目录名、`state.json` 的兜底目录名、
   以及卸载时识别 1.1.0 旧安装目录，全靠这个字符串对齐。
   `assert_shared_names()` 用 AST 取值后逐处比对，不一致就构建失败。

## 版本与发布

版本号遵循[语义化版本](https://semver.org/lang/zh-CN/) `MAJOR.MINOR.PATCH`，
每次变更的完整记录见 [`CHANGELOG.md`](CHANGELOG.md)。

**版本号的唯一来源是 `code_review/optimized/version_check.py` 里的 `APP_VERSION`。**
它同时驱动：程序内提示文字、安装向导顶栏、`payload.zip` 的 meta、PE 版本信息、发布的 Git tag。

两条构建期断言保证它漂不了（不一致就构建失败）：

- `check_toolchains()` —— 两份 version 文件里**四处**版本号
  （`filevers` / `prodvers` / `FileVersion` / `ProductVersion`）必须彼此一致且等于 `APP_VERSION`；
- `assert_copies_of_version()` —— `installer.APP_VERSION` 这个**有意的副本**必须相等。
  （`installer.py` 不直接 import `version_check`，是为了不让 `Setup.exe` 的依赖图里出现 `urllib`。）

> 这两条是踩坑换来的：改 1.0.0 → 1.1.0 时版本号一度只落地一半，
> 容器 meta 写着 `HAAVIK Photo 1.0.0`、向导顶栏显示 `v1.0.0`，而 exe 属性页已是 1.1.0 ——
> 而当时**所有校验都是绿的**。版本号是典型的"会被抄到很多地方"的东西，只能靠断言管。

| 位 | 什么时候 +1 |
|---|---|
| MAJOR | 不兼容的改动（改问答、改默认安全行为、改产物结构） |
| MINOR | 向后兼容的新功能（新增参数、新增审计章节、新增界面功能） |
| PATCH | 向后兼容的修复（错别字、布局裁切、资源漏打包） |

发布一条新版本 = **跑回归 → 重建 → 审计 → 打 tag → Release 附 `Setup.exe`**：

```powershell
# 1. 回归（改了对应模块就必跑）
python code_review/layout_test.py         # UI 布局，100%/125%/150% 三档缩放
python code_review/serial_test.py         # 序列号 + 月度闸门 + 图片工具
python code_review/update_check_test.py   # 更新提示与下载校验
python code_review/e2e_install_test.py    # 安装机制
# 2. 重建（含版本单源断言、资源嵌入断言、产品名一致断言）
python code_review/optimized/build.py
# 3. 审计（退出码必须为 0）
python code_review/verify_payload.py
# 4. 同步版本号：改 version_check.APP_VERSION，两份 version 文件 + installer 跟着改
# 5. 本机验收安装：python code_review/deploy_local.py
# 6. 提交 → tag vX.Y.Z → Release 上传 dist/Setup.exe
# 7. 把版本锚点 Gist 的内容改成新版本号
#    （不改的话，老版本用户看到的提示会指向一个错的版本号）
```

> **最省事的更新分发方式仍然是：重新发一个新的 `Setup.exe`。**

## 关于 XOR 混淆的澄清

`payload_codec.py` 里的 XOR 是**混淆编码，不是加密**：

- 密钥硬编码在源码里，任何人反编译都能在几分钟内还原；
- 它不提供任何机密性，也挡不住任何认真的安全分析；
- 把它当安全边界，只会换来杀软误报、代码不可读、构建不可复现 —— 而挡不住任何真正想看的人。

保留它的唯一理由是"让载荷在十六进制编辑器里不可读"，仅此而已。

真正有价值的是同一个文件里的 **CRC32 校验**：它能在安装器**写出文件之前**发现
"载荷被截断 / 换错文件 / 拷贝损坏"，把一类本来要到用户机器上才暴露的静默故障，
提前到构建期或安装期明确报错。

## 已知限制

1. 自签名证书 → 别人机器上显示"未知发布者"，SmartScreen 可能拦一次。
   遇到拦截的正解是**消除触发原因**（少一点伪装特征），不是加壳、加持久化、加反检测。
2. 从网络下载的 exe，首次运行前需右键 → 属性 → 勾选"解除锁定"。
3. 只支持 Vista 及以上（Python 3.8 / 3.12 本身不支持更早的系统）。
4. 杀软可能对"伪装成安装包"这个组合误报。这是该题材的固有代价，
   **不通过加强对抗来解决**。
5. **「有新版本」提示（以及将来的下载）依赖 GitHub 可达。** 版本锚点在 `gist.githubusercontent.com`，
   该域名在部分网络下不可达或极慢（超时设为 8 秒）。届时查询会静默失败、不显示提示 ——
   这**不影响**图片工具与闸门流程，也**不会**报错打扰对方；想知道有没有新版，直接问作者即可。
   （本机实测中位 0.4 秒，但在系统繁忙时可达 1.2 秒以上，所以超时给得比较宽。）
6. **月度闸门的"月份"取自本机系统时间。** 把系统时间往前/往后调，就能绕过或反复触发这一问 ——
   这是有意的：这道题是给人解的，不是用来卡人的，没必要为它加时间防篡改。
7. **`state.json` 删掉就等于"这个月没问过"。** 同上，也是有意为之。
