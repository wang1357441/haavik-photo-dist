# 代码审查标准与流程（CODE REVIEW STANDARD）

> 版本 1.0 · 适用范围：HAAVIK Photo 项目全集（含构建脚本、打包脚本、资源生成器）
> 配套文档：`CODE_REVIEW_REPORT.md`（逐文件审查结论）、`optimized/`（优化后代码）

---

## 0. 为什么需要这份标准

这个项目暴露了"没有审查机制"的典型症状，全部是**实际发生**的：

| 症状 | 本项目实例 |
|---|---|
| 缺陷藏在没人看的文件里 | `setup.py` 长到 56 MB，任何 IDE 打开即卡死 → 无人审查，缺陷存活至今 |
| 同一功能两套实现 | `inject_payload.py`（v1）与 `inject_payload_v2.py`（v2）并存，v1 已被完全取代却仍在被构建脚本调用 |
| 文档与产物脱节 | README 宣称 4 个 exe，`dist/` 里实际只有 2 个 |
| 工具链不可复现 | x64 的 spec 是 PyInstaller 6 格式，x86 的 spec 是 PyInstaller 5 格式 → 两种架构由不同大版本构建 |
| 错误被静默吞掉 | 资源缺失时 `continue`，把 `b"xxx_PLACEHOLDER"` 当真实资源写进用户磁盘 |
| 借"隐蔽性"之名牺牲可读性 | `chr(115)+chr(104)+...` 拼出 `shutdown`，导致代码无法 grep、无法审计 |

**核心原则：可审查性优先。** 一份没人能读完的代码，等于没有质量保证。

---

## 1. 原则

1. **审查是教学，不是关卡。** 每条意见要说明"为什么"，让作者下次能自己发现。
2. **优先序高于完备性。** 宁可只指出 3 个真问题，不要淹没在 30 条风格意见里。
3. **一次给完。** 不要跨多轮挤牙膏，每轮反复往返是最大的效率损耗。
4. **可读性 > 隐蔽性。** 任何以"防扫描/防分析"为由牺牲可读性的写法，默认拒绝。
5. **不阻塞原则。** 风格分歧不挡合并；正确性/安全性问题必须挡。
6. **证据驱动。** 意见要带文件 + 行号 + 复现路径，不接受"我感觉这里有问题"。

## 2. 严重级别定义

| 级别 | 名称 | 定义 | 典型例子 | 处理要求 |
|---|---|---|---|---|
| 🔴 **P0** | 阻断 | 会造成数据丢失、崩溃、安全漏洞，或让产品核心功能不可用 | 强制关机 `/t 0`；异常变量被 lambda 延迟引用导致报错本身崩溃；静默写坏用户文件 | **必须修**，修复前禁止合并/发布 |
| 🟠 **P1** | 严重 | 在特定条件下必然出错，或造成可复现的功能缺陷 | 32 位安装包在 64 位系统上判错架构；进度条首帧不绘制；桌面路径硬拼 | **必须修**，或书面记录已知风险并给出规避方案 |
| 🟡 **P2** | 建议 | 影响可维护性、性能、构建可复现性，不影响当前功能 | 56 MB 源码；重复实现；`hash()` 作为随机种子导致构建不可复现 | **应当修**，可排期，不阻断 |
| 💭 **P3** | 细节 | 命名、注释、风格、可选替代方案 | 未使用的 import；`abs(x-sx) <= 0`；`Image.LANCZOS` 的现代化写法 | 随手修，不强制 |

**"阻断"的判定标准（三问）**：
1. 会不会丢失/破坏用户数据？→ P0
2. 会不会让用户看到无法理解的故障？→ P1 以上
3. 三个月后换个人接手，能不能看懂？→ 不能则 P2 以上

## 3. 审查维度清单

### C. 正确性（Correctness）

- [ ] 边界条件：空值、零、最大最小值、首帧、空列表
- [ ] **延迟绑定**：`lambda` / 闭包是否捕获了循环变量或已失效的异常变量（`except ... as e` 中的 `e` 在块结束后即被删除）
- [ ] 并发：共享状态是否有锁/事件；`daemon` 线程被主线程退出强杀时的后果
- [ ] 计时：是否存在两个独立时间源（UI 倒计时 vs `sleep`）导致漂移
- [ ] 资源释放：文件句柄、`threading.Event`、`after` 回调是否清理
- [ ] 状态机：页面/步骤来回切换时，历史栈与页面状态是否自洽
- [ ] 失败路径：每个 `try` 的 `except` 分支是否都给了用户可理解的结果

### S. 安全与隐私（Security）

- [ ] **不做静默破坏**：任何写盘/删除操作前先校验，写盘用「临时文件 + `os.replace`」保证原子性
- [ ] **不吞异常**：`except: pass` 一律拒绝；至少记录日志
- [ ] **不伪装身份**：PE 元数据不得冒用第三方公司名/商标（法律风险 + 提高杀软命中率）
- [ ] **不引入不必要的风险面**：不在用户可写目录放伪造 `.dll`（DLL 搜索顺序风险）
- [ ] **路径解析**：不要硬拼 `~/Desktop` 这类路径，向系统 API 索取（重定向/OneDrive 会打破假设）
- [ ] **凭据**：不得硬编码密钥；若必须硬编码，注释中必须明确"这不是安全边界"
- [ ] **子进程**：使用列表参数而非字符串拼接（避免注入与转义问题）

### T. 整蛊/幽默类软件专项红线（Prank Safety Contract）

> 这是本项目的**特有标准**。整蛊程序与恶意软件的分界线，必须写下来、逐条打勾。

- [ ] **T1 知情同意**：仅用于事先知情并同意的朋友。README 与安装向导首页必须写明。
- [ ] **T2 不可逆伤害为零**：不得删除/加密/移动用户文件，不得改注册表、不装服务、不设自启动
- [ ] **T3 可随时退出**：任何时刻都存在**显式、一键、可见**的退出方式
- [ ] **T4 默认无害**：危险性最高的行为必须是**默认关闭**、需要操作者显式开启（如 `--real-shutdown`）
- [ ] **T5 有真实倒计时**：若实现真实关机，倒计时必须交给系统（`shutdown /s /t N`）而不是自己 `sleep`，且 `shutdown /a` 必须真正可用
- [ ] **T6 显示真相**：进入危险模式时界面必须有明示（如"⚠ 真实关机模式已启用"）
- [ ] **T7 无联网**：不发起任何网络连接
- [ ] **T8 不留残留**：卸载 = 删掉具名文件（`MyAlbum.exe` + `state.json`），不留任何系统痕迹。
  ⚠️ 安装位置默认是**桌面**，所以卸载**绝不能**按目录递归删 ——
  只能删那几个名字写死在常量里的文件
- [ ] **T9 不做杀软对抗**：不实现任何以"绕过安全软件检测"为目标的机制（见下方 4. 红线）

**T9 的执行标准（重要）**：当产出物需要"避免被安全软件拦截"时，正确解法**不是**加强对抗，而是**消除触发原因**：

| ❌ 错误解法 | ✅ 正确解法 |
|---|---|
| XOR 加密载荷"避开静态特征" | 载荷是良性的，无需隐藏；去掉伪装，让杀软看清它是无害的 |
| 伪造"微软文件"的 PE 元数据 | 写自己的产品名与"娱乐用途"说明 |
| 用 38 MB 垃圾数据"撑体积骗启发式" | 不需要骗；体积小反而启动更快 |
| `chr()` 拼接命令绕过硬编码特征 | 直接写 `shutdown`，让审计者一眼看懂 |

理由不是道德说教，而是**工程上算不过来**：对抗手段会把"良性玩笑"伪装成"恶意软件"，从而**提高**被杀软拦住的概率（这正是本项目 `Setup_x86.exe` 被 Defender 删除的原因），同时把法律与合规风险从"恶作剧"抬升到"规避安全软件"。收益为负。

### M. 可维护性（Maintainability）

- [ ] **单文件可读性**：任何源文件不得超过 ~1500 行、不得包含 >1 MB 的内联数据
- [ ] **单一职责**：一个模块一件事；功能重叠的脚本必须合并或删除
- [ ] **命名**：`setup.py` 这类会被工具自动发现的名字要避开
- [ ] **魔法数字**：提取为具名常量
- [ ] **死代码**：删除，不要靠注释保留
- [ ] **数据与代码分离**：大体量数据放资源文件，不进源码

### P. 性能（Performance）

- [ ] 逐字节/逐像素的 Python 循环 → 用批量操作替代
- [ ] 大数据是否被一次性读入内存（32 位进程尤其致命）
- [ ] UI 线程是否被 IO 阻塞
- [ ] 大常量是否会拖慢启动解析

### B. 构建与发布（Build & Release）

- [ ] **工具链一致**：同一产物的所有架构由同一大版本工具链构建
- [ ] **可复现**：同一输入重复构建应产出相同文件（禁止 `hash()` 等进程随机化种子）
- [ ] **不生成版本相关的构建文件**：`spec` 格式跨 PyInstaller 大版本不兼容 → 优先用命令行参数
- [ ] **产物核对**：`dist/` 实际内容必须与 README 声明一致
- [ ] **构建脚本可移植**：不得硬编码某台机器的绝对路径
- [ ] **架构正确性**：产物位数要用 PE 头**实测**，不能靠假设

### D. 文档（Documentation）

- [ ] README 与代码同步；不把"防御手段"当作卖点宣传
- [ ] 每个脚本文件头部写清：做什么、怎么用、为什么这么设计

## 4. 流程

```
  ┌─────────────┐
  │ 1. 提交前自检 │  作者按第 3 节清单自查，附上变更说明
  └──────┬──────┘
         ▼
  ┌─────────────────────────────────────────┐
  │ 2. 自动门禁（无人工介入）                  │
  │   · 语法编译（目标最低版本 Python）          │
  │   · 核心模块自检函数（self_test）           │
  │   · 构建可通过 + 产物位数实测               │
  │   · 载荷容器与 dist 一致性校验              │
  └──────┬──────────────────────────────────┘
         │ 任一失败 → 打回，不进入人工审查
         ▼
  ┌─────────────┐
  │ 3. 人工审查   │  逐文件过第 3 节清单；输出一份完整意见（不挤牙膏）
  └──────┬──────┘
         ▼
  ┌─────────────┐
  │ 4. 作者修改   │  逐条回应：已修 / 不修 + 理由
  └──────┬──────┘
         ▼
  ┌─────────────────────┐
  │ 5. 复核（只看改动）    │  确认 P0/P1 全部闭环
  └──────┬──────────────┘
         ▼
  ┌─────────────┐
  │ 6. 合并       │  合并门禁见下
  └──────┬──────┘
         ▼
  ┌─────────────┐
  │ 7. 发布归档   │  记录版本、产物哈希、当前工具链版本
  └─────────────┘
```

### 合并门禁（全部满足才可合并）

1. 自动门禁全绿
2. 无未闭环的 🔴 P0 / 🟠 P1
3. 「整蛊专项红线」T1–T9 逐条打勾（整蛊类功能变更时必须）
4. 新增/修改的行为有对应文档更新
5. 构建产物清单与 README 一致

### 单人项目的简化执行

本项目目前是单人开发，做不到"他人审查"。替代方案（务实且有效）：

- **把"审查者"角色交给工具**：把第 3 节清单变成一段可执行的检查脚本（本项目已有 `payload_codec.self_test()` 与 `verify_payload.py`）
- **强制"冷启动审查"**：每次改完，隔一天再看一遍，并强制回答一个问题——「如果我不是作者，我能看懂这段吗？」
- **每次变更写一段 CHANGELOG**，用"对使用者可观察的影响"来写，而不是"改了哪些文件"

## 5. 审查意见模板

```markdown
🔴 **P0 · 正确性：关机指令无法被取消**
文件：main.py:147-149

**现象**：倒计时线程只做 `time.sleep(60)` 后直接关机，没有任何取消检查。
用户在最后一秒点击「取消」，`shutdown /a` 执行成功，
但线程仍会在 60 秒整再次触发关机。

**为什么**：取消动作与触发动作之间没有共享状态，
两者是两条独立的执行路径。

**建议**：改用 `threading.Event`，让等待本身可被中断：
    if self._cancel.wait(remaining): return
```

**反例（不要这样写）**：
- ❌ "这里有点问题" —— 没说是什么问题、在哪个文件、怎么复现
- ❌ "建议全部重构成类" —— 范围过大，作者无法执行
- ❌ "风格不好" —— 未说明为什么影响正确性/可维护性

## 6. 度量指标

追踪这 5 个就够，多了没人看：

| 指标 | 含义 | 目标 |
|---|---|---|
| **缺陷逃逸率** | 发布后才发现的问题数 / 总问题数 | 逐版下降 |
| **P0/P1 存活时长** | 从发现到修复的时长 | < 7 天 |
| **单文件最大行数** | 最大的源文件行数 | < 1500 |
| **构建可复现性** | 同输入两次构建是否字节一致 | 100% |
| **文档-产物偏差** | README 声明与 `dist/` 实际的差异项 | 0 |

## 7. 例外流程（热修）

允许跳过人工审查、直接修复的情形**仅限**：

- 用户机器上的数据正在被破坏
- 已发布产物存在无法启动的问题

流程：修复 → 在 CHANGELOG 标注 `[HOTFIX]` → 24 小时内补做完整审查 → 补写根因分析（不是"我改好了"，而是"为什么会漏掉"）。
